# Kerdion - Authentication & Authorization (Phase 5)

## 📌 Overview
Phase 5 introduces user accounts and JWT-based authentication to the Kerdion backend. Until now, every endpoint built in Phase 4 was fully public. In this phase we added a `users` table, password hashing, JWT issuing/verification, register/login endpoints, and locked down both the REST prediction endpoints and the live WebSocket stream behind a valid access token. We also introduced a `USER` / `ADMIN` role distinction so future admin-only features (e.g. manually triggering the ML pipeline, managing users) have a foundation to build on.

## 🏗️ Tech Stack Additions
* **Password Hashing:** `passlib` (bcrypt backend)
* **JWT Issuing/Verification:** `python-jose`
* **Form-Encoded Login:** `python-multipart` (required by FastAPI's `OAuth2PasswordRequestForm`)
* **Email Validation:** `email-validator` (required for Pydantic's `EmailStr`)

## 🚀 Key Features Implemented

### 1. User Model & Migration (`app/models/user.py`)
* New `users` table: `id`, `email` (unique, indexed), `hashed_password`, `role` (`USER` / `ADMIN`, native Postgres enum), `is_active`, `created_at`.
* Alembic migration `7c339c69ebbc_add_users_table.py`. Note: the autogenerated `downgrade()` was patched to explicitly drop the `user_role` Postgres enum type — native enums aren't tied to their owning table's lifecycle, so without this fix a `downgrade` followed by `upgrade` would fail with "type already exists".

### 2. Security Core (`app/core/security.py`)
* `hash_password` / `verify_password` — bcrypt password hashing via `passlib`.
* `create_access_token` / `decode_access_token` — signs and verifies JWTs using `SECRET_KEY`, with configurable `JWT_ALGORITHM` (default `HS256`) and `ACCESS_TOKEN_EXPIRE_MINUTES` (default 60).

### 3. User Schemas & CRUD (`app/schemas/user.py`, `app/crud/crud_user.py`)
* `UserCreate`, `UserResponse`, `Token`, `TokenPayload` Pydantic schemas.
* `get_user_by_email`, `create_user` (hashes the password before insert), `authenticate_user` (verifies email + password, returns `None` on any mismatch).

### 4. Auth Endpoints (`/api/v1/auth/`)
* **`POST /auth/register`**: Creates a new user (defaults to `USER` role). Rejects duplicate emails with `400`.
* **`POST /auth/login`**: Accepts OAuth2 form-encoded credentials (`username` = email, `password`), returns a `Token` on success or `401` on invalid credentials.

### 5. Auth Dependencies (`app/api/deps.py`)
* `get_current_user`: Decodes the bearer JWT, loads the corresponding user, and rejects the request with `401` if the token is missing/invalid/expired or the user is inactive.
* `get_current_admin_user`: Builds on `get_current_user`, rejecting non-`ADMIN` users with `403`. Not wired into any route yet, but ready for future admin-only endpoints.

### 6. Protected Routes
* All `/api/v1/predictions/*` REST endpoints now require a valid `Authorization: Bearer <token>` header (enforced at the router level via `get_current_user`).
* The `/api/v1/ws/live-predictions` WebSocket now requires a `?token=<jwt>` query parameter, since browsers cannot set custom headers during a WebSocket handshake. Connections with a missing, invalid, or expired token are closed with code `1008` (policy violation).

## 📡 Auth Flow
1. **Register:** Client `POST`s email/password to `/auth/register`. Password is hashed with bcrypt before storage.
2. **Login:** Client `POST`s email/password (as OAuth2 form data) to `/auth/login`. On success, receives a signed JWT with the user's email as the `sub` claim.
3. **Authenticated Requests:** Client sends `Authorization: Bearer <token>` on REST calls, or `?token=<token>` on the WebSocket URL. `get_current_user` decodes the token, looks up the user, and injects it into the route — or rejects the request if anything doesn't check out.

## 🛠️ Developer Guide: Testing the Auth Flow

### 1. Register a user
```bash
curl -X POST http://localhost:8000/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email": "you@example.com", "password": "yourpassword"}'
```

### 2. Log in and get a token
```bash
curl -X POST http://localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=you@example.com&password=yourpassword"
```

### 3. Call a protected endpoint
```bash
curl http://localhost:8000/api/v1/predictions/ \
  -H "Authorization: Bearer <paste-access-token-here>"
```

### 4. Connect to the protected WebSocket
```
ws://localhost:8000/api/v1/ws/live-predictions?token=<paste-access-token-here>
```

## ⚙️ Infrastructure: Faster Docker Rebuilds
Alongside Phase 5, the Dockerfile was restructured to stop the entire dependency layer (including PyTorch) from reinstalling on every small dependency change:
* Heavy, slow-changing ML dependencies (`torch`, `pandas`, `numpy`, `scikit-learn`, `arch`, `joblib`) now live in their own Poetry dependency group (`[tool.poetry.group.heavy.dependencies]`) and are installed in their own Docker layer.
* Lightweight, frequently-changing dependencies (FastAPI, auth libraries, etc.) install in a separate, later layer.
* BuildKit cache mounts (`--mount=type=cache`) were added for Poetry/pip's package cache, so even when a rebuild is genuinely required, already-downloaded wheels are reused instead of re-fetched from PyPI.

This does not change any resolved dependency versions or runtime behavior — it only affects how the Docker image is built.
